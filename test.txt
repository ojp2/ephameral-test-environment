I finished correlating the Elasticsearch side with the 8:35–8:38 outage.

The main issue was search thread-pool saturation on the ProSearch data nodes. Around 8:33, several searches became much slower than normal. Traffic only increased slightly, but latency jumped enough for the search queues to grow to their limit of 1000. Once that happened, requests started timing out/rejecting, which lines up with the ProSite `curl_exec failed` errors. The cluster recovered once the backlog drained.

The key capacity issue is that each data pod has 2.5 CPUs available, but Elasticsearch is configured with `allocated_processors=1`, so each data node only gets a very small search thread pool. Elasticsearch uses this processor value to size its thread pools.

Historical metrics also show similar weekday queue activity around this same time, but normally it clears before reaching the limit. Today the searches were slower and pushed it over the threshold.

I don’t see evidence that the 2 `es-prosearch-client` pods were the primary bottleneck. We also saw no pod restarts, OOMs, GC issues, shard imbalance, DNS, or service failures.

Recommendation: correct the processor configuration on the data nodes to match their actual CPU allocation, add alerting for search queue/rejections/latency, enable better slow-query visibility, and plan an upgrade from ES 6.2.3. We should validate/load-test the processor change before applying it in prod.
