Good question. I dug into that part specifically.

It looks like most of the requests weren't getting an ES error back because they were sitting queued waiting on the saturated data nodes. The PHP cURL timeout is around 30s, while nginx would wait longer for the upstream response. So PHP gave up first and closed the connection, which is why nginx recorded 499s and the app surfaced it as `curl_exec failed` instead of getting a clean 429/5xx back from Elasticsearch.

I checked the client logs as well and during this window we had 499s, but no corresponding 429/503/504 responses. That lines up with the requests timing out while queued rather than Elasticsearch returning an HTTP error first.

So the client pods were still functioning as coordinators; they were waiting on the backed-up search work downstream and the application timeout fired before a response made it back.
